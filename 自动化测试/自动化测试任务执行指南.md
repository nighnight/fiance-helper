# 自动化测试任务完整执行指南

## 一、项目背景与目标

### 1.1 项目介绍
本项目为 **个人财务记账与分析助手**（finance-helper），是一个基于 Spring Boot 3.2.0 + MyBatis + Thymeleaf 的个人财务管理系统。

**技术栈：**
- 后端：Spring Boot 3.2.0、Java 17、Maven、MyBatis、MySQL 8.0
- 前端：Thymeleaf、Bootstrap 5、jQuery、ECharts
- 安全：Spring Security Crypto（BCrypt 加密）、HttpSession 登录鉴权

**核心功能模块：**
- 用户管理（注册、登录、密码修改）
- 收支记录（新增、修改、删除、查询、Excel 导出）
- 账户管理（银行账户、现金、电子钱包）
- 预算管理
- 分类管理（收入/支出类别）
- 统计报表（饼图、趋势图、关键指标）
- 数据同步与文件上传

### 1.2 任务目标

构建完整的自动化测试体系，实现以下四个核心目标：

1. **掌握分层自动化测试设计**：区分「研发侧代码级测试」和「客户侧接口自动化测试」，构建测试金字塔
2. **掌握 CI/CD 流水线搭建**：使用 Gitee 平台实现「代码提交 → 自动触发测试 → 质量门禁 → 自动回归」的全流程自动化
3. **掌握自动化测试代码编写**：基于本项目，编写可落地、可维护的 JUnit 测试与接口自动化测试用例
4. **建立质量闭环思维**：理解自动化测试在软件工程全流程中的定位

### 1.3 测试范围（本指南聚焦两个核心模块）

| 模块 | 测试内容 | 负责人 |
|------|---------|--------|
| 用户登录模块 | 注册、登录、密码加密、输入校验、边界条件、异常处理 | 本人 |
| 收支记录模块 | 新增收入/支出、余额联动、超额拦截、修改删除、查询 | 本人 |

> 注：本项目为单人全包模式，不分组。两个模块的代码级测试 + 接口回归测试 + CI/CD 流水线均由本人完成。

## 二、CI/CD 概念解释

### 2.1 什么是 CI/CD？

**CI（Continuous Integration，持续集成）**
- 开发人员频繁地将代码合并到主干分支
- 每次合并自动触发编译、单元测试、代码检查
- 目的：尽早发现问题，避免集成地狱

**CD（Continuous Delivery/Deployment，持续交付/部署）**
- 代码通过测试后，自动打包、发布到测试环境或生产环境
- 目的：缩短从代码提交到用户可用的时间

### 2.2 在本项目中的 CI/CD 流程

```
开发者提交代码 (git push)
    ↓
Gitee Go 自动触发流水线
    ↓
Stage 1: 编译 (mvn compile)
    ↓
Stage 2: 代码级单元/集成测试 (mvn test)
    ↓  [质量门禁] 测试失败 → 阻断流水线，无法合并代码
    ↓  [测试通过] 生成覆盖率报告
    ↓
Stage 3: 打包 (mvn package)
    ↓
Stage 4: 客户侧接口回归测试 (Apifox CLI)
    ↓  [回归失败] 阻断合并
    ↓  [全部通过] 允许代码合并
```

### 2.3 质量门禁（Quality Gate）

质量门禁是 CI/CD 中的关键概念，指代码合并前必须满足的最低质量标准：

- **单元测试通过率 100%**：任何测试失败都阻止合并
- **代码覆盖率 ≥ 80%**：核心业务逻辑必须被测试覆盖
- **接口回归测试通过**：端到端业务流程必须正常
- **两层测试有先后依赖**：代码级测试通过后，才触发客户侧回归测试

## 四、修复已知缺陷（先修再测）

在编写自动化测试之前，必须先修复手动测试阶段发现的两个核心缺陷，否则自动化测试会失败。

### 4.1 Bug-01：支出金额超过余额时扣成负数（P0 致命缺陷）

**问题描述**：当用户新增一笔支出记录，金额大于账户余额时，系统没有拦截，导致余额变成负数。

**修复位置**：`src/main/java/com/finance/service/impl/FinanceRecordServiceImpl.java`

**修复逻辑**：在新增支出记录前，校验账户余额是否充足。不足时抛出 `BusinessException`，阻止记录保存。

**关键代码修改思路**：
1. 在 `addRecord` 方法中，判断记录类型为「支出」时：
2. 查询对应账户的当前余额
3. 如果 `支出金额 > 账户余额`，抛出异常："账户余额不足，无法完成支出"
4. 确保数据库事务回滚，余额不被修改

**测试验证点**：
- 余额充足时，正常支出，余额正确扣减
- 余额不足时，抛出异常，余额不变，无新记录产生
- 余额刚好等于支出金额时，正常执行，余额变为 0

### 4.2 Bug-02：用户注册时用户名/昵称可注入表情/标签字符（P1 严重缺陷）

**问题描述**：注册时用户名和昵称输入框没有校验，可以输入表情符号、HTML 标签等特殊字符，存在 XSS 安全风险。

**修复位置**：`src/main/java/com/finance/controller/SysUserController.java` 或 `src/main/java/com/finance/service/impl/SysUserServiceImpl.java`

**修复逻辑**：在注册接口中对 `username` 和 `nickname` 增加正则校验，只允许中文、英文、数字、下划线。

**正则表达式**：`^[a-zA-Z0-9_一-龥]+$`

**校验规则**：
- 用户名：3-20 位，只允许中英文、数字、下划线
- 昵称：2-20 位，只允许中英文、数字、下划线
- 不符合规则时，返回错误提示："用户名/昵称只能包含中英文、数字和下划线"

**测试验证点**：
- 正常中英文用户名注册成功
- 包含表情符号（如 😀）注册失败
- 包含 HTML 标签（如 `<script>`）注册失败
- 包含特殊符号（如 `@#$%`）注册失败

1. 点击左侧「自动化测试」→「新建测试步骤」
2. 按上述 5 个流程，逐个添加接口请求
3. 配置每个请求的：
   - URL（如 `http://localhost:8080/user/login`）
   - 请求方法、参数、Body
   - 后置操作：提取 Cookie / Token（本项目使用 HttpSession，Apifox 自动管理 Cookie）
   - 断言：状态码、响应体字段值、响应头

#### 步骤 4：创建测试用例并关联步骤
1. 点击「测试用例」→「新建用例」
2. 将测试步骤按顺序拖入用例
3. 设置用例间的变量传递（如从登录响应中提取用户 ID，传给后续步骤）

#### 步骤 5：本地运行验证
1. 启动本地应用：`mvn spring-boot:run`
2. 在 Apifox 中点击「运行」
3. 确认所有断言通过

#### 步骤 6：导出 CLI 命令
1. 测试用例全部通过后，点击「导出」→「CLI 命令」
2. 复制命令，保存备用（用于 CI/CD 流水线）

示例 CLI 命令：
```bash
apifox run https://api.apifox.com/api/v1/projects/xxx/test-groups/xxx \
  -r html,json \
  --out-dir ./apifox-report
```

### 6.4 Fallback 方案（备用）

若 Apifox CLI 在 Gitee Go 环境中安装失败，准备 `scripts/api-smoke-test.sh` 脚本：

```bash
#!/bin/bash
set -e

BASE_URL="http://localhost:8080"

echo "=== 接口冒烟测试开始 ==="

# 1. 注册
curl -s -X POST "$BASE_URL/user/register" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "username=testuser&nickname=测试&password=123456" | grep -q "success"
echo "✓ 注册通过"

# 2. 登录（保存 Cookie）
curl -s -c cookies.txt -X POST "$BASE_URL/user/login" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "username=testuser&password=123456" | grep -q "success"
echo "✓ 登录通过"

# 3. 查询记录列表
curl -s -b cookies.txt "$BASE_URL/record/list?page=1&size=10" | grep -q "data"
echo "✓ 查询列表通过"

# 4. 新增收入
curl -s -b cookies.txt -X POST "$BASE_URL/record/add" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "type=收入&amount=500&accountId=1&categoryId=1" | grep -q "success"
echo "✓ 新增收入通过"

# 5. 导出 Excel
CONTENT_TYPE=$(curl -s -b cookies.txt -o /dev/null -D - "$BASE_URL/record/export" | grep -i "content-type" | tr -d '\r')
echo "$CONTENT_TYPE" | grep -q "spreadsheet"
echo "✓ 导出 Excel 通过"

echo "=== 接口冒烟测试全部通过 ==="
```

## 七、Gitee Go CI/CD 流水线配置

### 7.1 流水线设计

在项目根目录创建 `.gitee-ci.yml`：

```yaml
stages:
  - compile
  - unit-test
  - package
  - integration-test

variables:
  MAVEN_OPTS: "-Dmaven.repo.local=.m2/repository"
  MAVEN_CLI_OPTS: "-B -e"

cache:
  paths:
    - .m2/repository

# Stage 1: 编译
compile:
  stage: compile
  image: maven:3.9-eclipse-temurin-17-alpine
  script:
    - mvn $MAVEN_CLI_OPTS compile
  artifacts:
    paths:
      - target/
    expire_in: 1 hour

# Stage 2: 单元/集成测试（质量门禁）
unit-test:
  stage: unit-test
  image: maven:3.9-eclipse-temurin-17-alpine
  script:
    - mvn $MAVEN_CLI_OPTS test jacoco:report
  artifacts:
    paths:
      - target/site/jacoco/
    reports:
      junit: target/surefire-reports/TEST-*.xml
    expire_in: 1 week
  coverage: '/Total.*?([0-9]{1,3})%/'
  allow_failure: false  # 失败阻断流水线

# Stage 3: 打包
package:
  stage: package
  image: maven:3.9-eclipse-temurin-17-alpine
  script:
    - mvn $MAVEN_CLI_OPTS package -DskipTests
  artifacts:
    paths:
      - target/*.jar
    expire_in: 1 week

# Stage 4: 客户侧回归测试
integration-test:
  stage: integration-test
  image: maven:3.9-eclipse-temurin-17-alpine
  script:
    # 使用测试配置启动应用（后台运行）
    - java -jar target/*.jar --spring.profiles.active=test &
    - APP_PID=$!
    - sleep 30
    
    # 尝试使用 Apifox CLI（如果项目中已配置）
    - npm install -g apifox-cli 2>/dev/null || echo "Apifox CLI install skipped"
    - |
      if command -v apifox &> /dev/null; then
        apifox run ... -r html,json --out-dir ./apifox-report || true
      else
        echo "Using fallback smoke test script"
        chmod +x scripts/api-smoke-test.sh
        bash scripts/api-smoke-test.sh
      fi
    
    # 停止应用
    - kill $APP_PID || true
  artifacts:
    paths:
      - apifox-report/
    expire_in: 1 week
  allow_failure: false  # 失败阻断流水线
  dependencies:
    - package
```

> **注意**：Gitee Go 的具体 YAML 语法可能略有差异，创建后需在 Gitee 页面上验证。

### 7.2 提交并验证流水线

```bash
git add .gitee-ci.yml scripts/api-smoke-test.sh
git commit -m "feat: 添加 Gitee Go CI/CD 流水线配置"
git push gitee master
```

推送后，在 Gitee 仓库 →「DevOps」→「Gitee Go」→「流水线」中查看自动触发的构建。

### 7.3 分支保护与质量门禁

1. 进入 Gitee 仓库 →「管理」→「仓库设置」→「分支管理」
2. 找到 `master` 分支，点击「保护」
3. 开启以下选项：
   - ☑ 禁止强制推送
   - ☑ 开启分支保护
   - ☑ 合并前需要通过流水线检查
   - ☑ 合并前需要审批（可设置为 0 人，仅演示用）
4. 保存设置

**验证门禁**：
1. 故意修改一个测试用例使其失败（如把预期结果写错）
2. Push 到 Gitee
3. 观察流水线在 `unit-test` 阶段失败
4. 尝试合并 PR，系统提示「流水线未通过，无法合并」
5. 修复测试后重新 Push，流水线通过，PR 可正常合并

## 十一、常见问题 FAQ

**Q1：为什么必须先修复 Bug 再写测试？**
> 如果先写测试，测试会按照「正确的业务规则」去断言，而现有代码有 Bug，测试会失败。修复 Bug 后，测试才能通过，这样测试本身就成为了回归验证工具。

**Q2：覆盖率 80% 怎么算？是整个项目还是单个模块？**
> 考核要求指「核心代码测试覆盖率」，聚焦你负责测试的两个模块即可。Jacoco 报告会分别展示每个类的覆盖率。

**Q3：Gitee Go 免费版够用吗？**
> 够用。免费版有每月构建时长限制，但本项目规模小、构建快，足够使用。如果担心超时，可在本地充分验证后再 push。

**Q4：Apifox CLI 在 Gitee Go 里装不上怎么办？**
> 已准备 fallback 方案（`scripts/api-smoke-test.sh`），用 curl 验证核心接口。考核时只要能展示「接口自动化测试在流水线中执行」即可，不强制要求必须用 Apifox CLI。

**Q5：HttpSession 在接口测试中怎么处理？**
> Apifox 客户端自动管理 Cookie（包括 session）。如果用 curl 脚本，需加 `-c cookies.txt -b cookies.txt` 参数保存和发送 Cookie。

**Q6：H2 数据库和 MySQL 语法不兼容怎么办？**
> 在 JDBC URL 中加 `MODE=MySQL` 参数，H2 会模拟 MySQL 语法。若还有不兼容（如特定函数），可在 `schema-h2.sql` 中调整为标准 SQL。
